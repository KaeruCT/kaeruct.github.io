For a coding agent, the input usually consists of the existing codebase and whatever the user prompted. Of course, the prompt will lead the agent to fetch additional information related to the task such as tickets, external documentation, and such.

The existing codebase includes code, but also documentation. Specifically the files the agents are configured to look at such as `AGENTS.md` or `CLAUDE.md`. It is my opinion that these files should not contain any information that is inferrable from the codebase such as commands to run or file structure. Coding harnesses are fully able to examine the existing codebase to determine these things. [This study by Gloaguen et al.](https://arxiv.org/abs/2602.11988) found that `AGENTS.md` files don't improve coding agent performance.

However, it can be argued that repeating this information in the file can save some time because the agents would follow the instructions immediately without any additional discovery step needed. In that case, I think some autogenerated documentation can be used to get the best of both worlds (human-written documentation and agent-specific documentation). I just prefer not to do it because it seems like an over-optimization. 

What is most relevant for these files are concepts that are not obvious from the codebase, such as business context, or why certain decisions were made (for example ADRs). The current best practice is to keep the `AGENTS.md` lean, ideally written by a human and heavily curated. It can reference more specific documentation (like a table of contents) so the agent knows where to look when working on specific parts of the system.
